§1 根因（宿主源码，逐字见 013_p3_bom_filter_root.txt 的 [A]/[B] 段）
------------------------------------------------------------------
api.js 的 getBomFile 包装把列参数拼成 d.tableAttrKeys：

    if(s) for(const p of s){ const m={title:p,value:p,order:0,key:0}; hne(p,m); push(m) }   // statistics，过 hne
    if(a) for(const p of a){ const m={title:p,value:p,order:0,key:0};        push(m) }      // property，不过 hne
    ... d.tableAttrKeys = d.tableAttrKeys.map((p,m)=>({...p, orderWeight: len-m}))
    if(o){ const p = d.tableAttrKeys.map(m=>m.value);
           for(const m of o) if(m.property==="No."&&(m.property="Number"), p.includes(m.property)) {...}
                             else return }                                                    // 缺列 = 整次调用返回 undefined

hne `'No.'` → value `'Number'`（BOM 引擎给序号列用的值）。两条结论：

1. **同一列名给两处就会出两列**（宿主不去重）——preset 原先把 `No.`/`Quantity` 既放 statistics
   又放 property（15 列全表），于是 tableAttrKeys 17 条、表头 17 列：第 13 列 `No.`/`Number`、
   第 15 列第二个 `Quantity`，与第 1 列 `序号`、第 3 列 `数量` 重复。
2. **不能反过来删 statistics**：只有 statistics 这条路径会把 `'No.'` 变成 `'Number'`，而列检查
   `p.includes('Number')` 找不到就 `return` —— 整次调用不返回任何文件（不是"表头少两列"，是
   **BOM 文件都没有**）。所以修法是"两列表互斥、并集 = 15 列"，不是"二选一删掉"。

### 真机过程里撞到的事（重要，已写进 docs/bridge.md §12 附近）
daemon 只保留**一个** connector 连接，而本机开着**多个编辑器窗口**（审计日志
`013_p3b_audit_windows.txt`：同一分钟内 hello 帧分别为 connector=0.4.10 / 0.4.9 / 0.4.10，
不同 socket），每个窗口有自己的扩展存储（各自的 build 版本）与各自的焦点工程，于是
"哪个 build 在答"和"焦点在哪个工程"随"最后注册的窗口"一起翻——这就是任务书里记的"焦点漂移"。
后果：**R1 全绿的导出也可能是旧 build 答的**。本次就是这样：第一次 R1 干净（毕设板 + PCB1）的
导出回来仍是 **17 列**（旧 preset），窗口报的版本同样是 0.4.10 —— 两个 0.4.10 靠版本号根本区分不了，
最后靠"表头 17/15"这个**行为**判定。处置：给"占着板子的那个窗口"重推同一版本的 bundle
（`sys.self_update`，179530 B）→ 该窗口页面重载 → 下一次导出即为 **15 列**（16:49:31 → 16:49:47）。
**结论：同一版本重推是生效的**，不需要 bump 版本（本次未 bump，仍 0.4.10）。
证据链：outputs/013_p3_evidence/013_p3b_attempts.jsonl（逐次 connector/project/active/列数/自更新记录）、
013_p3b_stale/（旧 build 的 17 列产物，留档不交付）、013_p3b_audit_windows.txt。
