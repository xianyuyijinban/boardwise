一、connector 现有打包流程
--------------------------------------------------------------------------------

1.1 npm 脚本（connector/package.json，version 0.4.10，private: true，type: module）
    build      node build.mjs
    package    node build.mjs && node package.mjs
    typecheck  tsc --noEmit
    test       node build.mjs && node --test "tests/**/*.test.mjs"
    devDependencies：@jlceda/pro-api-types ^0.4.25、esbuild ^0.28.2、typescript ^7.0.2
    **没有 engines 字段**：Node 版本下限在 package.json 里没有声明（见 1.9）。

1.2 build.mjs 出两个产物（都在 connector/dist/）
    - dist/index.js —— 侧载产物。esbuild 打包成 iife，globalName = edaEsbuildExportName
      （与官方脚手架/easyeda-agent 一致，编辑器按这个名字找 activate/菜单函数）。
      同时 define 注入 __BOARDWISE_VERSION__（取自 package.json.version）与
      __BOARDWISE_UUID__（取自 extension.json.uuid）。
    - dist/esm/*.mjs —— 同一份源码的 ESM 版本，专给 node --test 用（splitting: true，
      保证测试里跨模块 instanceof ActionError 成立）。
    当前树下 dist/index.js = 179,530 B（2026-09-21 21:09）。

1.3 package.mjs 打 .eext
    - .eext 就是 zip（deflate），**归档根目录**只有两个条目：extension.json、dist/index.js
      （dist/esm/ 故意不进包）。editor 读 extension.json 的 entry = "./dist/index"。
    - 确定性输出（固定 DOS 时间戳 + 固定条目顺序），同一份源码字节一致。
    - 只用 node:zlib 手写 zip（deflateRawSync + crc32），没有第三方依赖。
    - 默认输出：connector/boardwise-connector-<extension.json 的 version>.eext；
      可用 --out <path> 覆盖。
    - 文件头注释自述："layout conventional, not yet confirmed on a real sideload"。
      实则真机多次侧载成功（012/013 各版本），这句注释已过时（存疑项，见第七节）。

1.4 **版本号有两处，必须同改**：connector/package.json 的 version 与
    connector/extension.json 的 version（前者进 bundle 常量、后者进 .eext 文件名与
    connectorVersion 上报）。012 的 §十 已把这条写进任务书；doctor 的
    "运行中的 connector 版本与仓库一致"检查读的正是 extension.json。

1.5 产物先例（这是关键：路径与命名已固化）
    `ls connector/*.eext` = 26 个，0.3.5（9-14 11:42）→ 0.4.10（9-21 16:37）。
    最新两个：boardwise-connector-0.4.10.eext 43,337 B（013 realhost verification 打的，
    也是当前编辑器里跑的那个版本）、0.4.9.eext 41,688 B。
    **全部落在 connector/ 根目录，不是 dist/**——012 曾为此专门裁定"以实际为准，不改路径"。

1.6 分发方式：.gitignore 第 13 行 `connector/*.eext`、第 11 行 `connector/dist/`，
    两者都不入库 → 朋友拿到的 .eext 靠人工传（U 盘/网盘/IM 文件），不进 git。
    015（规则 m2）没动 connector，所以 0.4.10 仍是当前最新产物。

1.7 仓库里已有的"不重装就升级"通道：`boardwise bridge update-connector`。
    默认读 connector/dist/index.js + connector/extension.json，base64 走 sys.self_update
    写进编辑器 IndexedDB，然后 connector 自己刷新页面。老手可以
    `npm run build` + `bridge update-connector --yes`，不必重新导入 .eext。

1.8 锁文件状况（决定 build-connector.bat 能不能用 npm ci）
    connector/package-lock.json 的 root 条目是 name=connector / version=1.0.0，
    与 package.json（boardwise-connector / 0.4.10）**不一致**。
    实测（只做校验、不落盘）：`npm ci --dry-run --no-audit --no-fund` → 退出 0，输出
    "up to date in 407ms"；前后对比 connector/ 下全部文件的大小+mtime、package.json /
    package-lock.json / extension.json 的 sha256、node_modules 目录清单 → **完全一致**
    （npm 11.12.1 的 ci 校验只比对依赖清单，不比对 root 的 name/version）。
    结论：`npm ci` 在 connector/ 可用，build-connector.bat 可以用它。
    但 root 字段的漂移迟早会被别的工具介意——建议以后顺手 `npm install` 刷新锁文件。

1.9 Node 版本硬门槛（实测 + 官方发布说明核对）
    package.mjs 用 `zlib.crc32`，该 API **新增于 Node v20.15.0**（v22.2.0 也有；
    来源：nodejs.org 的 v20.15.0 / v22.2.0 发布说明）。→ 自己构建 .eext 需要
    Node 20.15 以上（建议 LTS 22/24）。本机 node v24.15.0、npm 11.12.1。
    朋友只拿现成 .eext 的话完全不需要 Node。

二、Python 包现状
--------------------------------------------------------------------------------

2.1 打包配置只有 pyproject.toml（PEP 621），**没有 setup.py / setup.cfg**：
    - build-backend = setuptools.build_meta，requires = ["setuptools>=68"]
      → `pip install -e .` / `pip install .` 都需要能拿到 setuptools（隔离构建环境会去下载）
    - name = boardwise，version = 0.1.0
    - **requires-python = ">=3.10"**（3.10 门槛的唯一权威来源；doctor 不检查 Python 版本）
    - 唯一运行时依赖：**websockets>=13.0**（daemon 用 websockets.asyncio.*，13.0 起；
      开发对照 17.1）。其余全标准库，离线审查路径不需要任何依赖。
    - [project.scripts] boardwise = "boardwise.cli:main"
    - packages.find where = ["src"]

2.2 入口有三条等价路径（用于脚本里怎么调）
    - 控制台脚本：.venv\Scripts\boardwise.exe（pip 装出来的）
    - `python -m boardwise.cli ...`（cli.py 末尾有 `if __name__ == "__main__": sys.exit(main())`）
    - **没有 boardwise/__main__.py**，所以 `python -m boardwise` 不成立。
    脚本内统一用 `.venv\Scripts\python.exe -m boardwise.cli ...`（不依赖 PATH、
    不依赖激活 venv、不依赖 pip 有没有生成 .exe）。

2.3 版本号也有两处：pyproject.toml 的 version=0.1.0 与
    src/boardwise/__init__.py 的 __version__="0.1.0"（doctor 的本地版本取后者）。
    本次不改版本号（§D 不动版本）。

2.4 **必须 editable 安装**（这是 install.bat 选 `pip install -e .` 的根据）：
    - CLI 里 `bridge update-connector` 的默认 bundle 路径是
      `Path(__file__).resolve().parents[2] / "connector" / ...` → 要求源码 checkout 就在原地；
      非 editable 装法（wheel 进 site-packages）下 parents[2] 指向 site-packages 上层，
      connector/ 不在那里。
    - doctor 的 connector 版本检查读 connector/extension.json；读不到就 **SKIP**
      （代码自述"不是仓库里的运行方式"）。wheel 装法会让这一项永久 SKIP。
    - blocklib/ 下的默认值（blocklib/parts.json、blocklib/blocks.portmeta.json）是
      **相对当前目录**的路径 → 使用时要在仓库根目录跑。这些都不是包装得进去的东西。
    结论：给朋友的安装方式 = 从仓库里 `pip install -e .`，仓库留在原地别删。

2.5 本机 .venv 现状（只记录，没动它）
    Python 3.14.4、pip 26.0.1、websockets 17.1、boardwise 0.1.0（editable，指向 E:\boardwise）。
    **venv 里没有 setuptools** → 每次 `pip install -e .` 都要联网拉构建后端（配合 websockets，
    首次安装至少要能访问 PyPI；离线机器装不上，install.bat 的失败提示里要写清这一点）。

五、据此实现的安装脚本（静态设计依据）
--------------------------------------------------------------------------------

- install.bat：py -3 优先、退化到 python，用一次性 Python 表达式判定
  `sys.version_info[:2] >= (3,10)`（退出码 0/9 分流）；没有或版本低 → 官网链接 + 退出 1；
  建/复用 .venv → 升 pip（失败不致命）→ `pip install -e .` → `.venv\Scripts\python.exe
  -m boardwise.cli doctor`（**红项不算安装失败**：首装时 daemon 没起、编辑器没装扩展是正常的，
  脚本按退出码分流文案）→ 打印下一步（装 .eext → 起 daemon → 复查 doctor → 第一次 review）。
  每一步失败都有中文提示与常见的具体原因。
- start-daemon.bat：可见窗口、标题 "boardwise daemon"；先查端口是否已被监听（已有 daemon
  → 直接打印连接状态并退出，不再起第二个）；然后窗口内每 60 秒打印一次连接状态行
  （`.venv\Scripts\python.exe -m boardwise.cli bridge status | findstr connector:`，
  在同一个控制台里跑，daemon 自己的横幅与配对公告也在同一窗口）；daemon 退出后再打一次状态。
- stop-daemon.bat：netstat 找监听端口的 PID → tasklist 核对 → taskkill /F；找不到就说
  "已经停了"，不猜不杀别的进程。
- build-connector.bat：封装现有 npm 流程（`npm ci` → `npm run package`），先查 node 在不在、
  版本 ≥ 20.15，再打印产物绝对路径（dir /o-d 取最新 `boardwise-connector-*.eext`）。
- 端口口径：脚本读 BOARDWISE_PORT，缺省 61190（与 daemon.resolve_port 一致）。
- **编码口径（关键，见 §6.5）**：四个 .bat 存 **ANSI/GBK + CRLF**，第 2 行 `chcp 936`。
  这是实测出来的：cmd 按控制台代码页解析批处理文件，UTF-8（无 BOM）+ `chcp 65001` 会被
  解析错位（把某行的尾巴当命令执行）；UTF-8 + BOM 会让第 1 行 `@echo off` 失效。
  维护方式：UTF-8 母本留档在 `.tmp_018_d_probe/utf8/*.bat`（一次性证据目录，未入库），
  改完用下面这条命令重发（Python 显式二进制读写，不碰行尾；本次已用它对四个脚本各验过一次，
  产物与 shipped 文件逐字节相同）：
  ```bash
  E:/boardwise/.venv/Scripts/python.exe -c "import pathlib,sys;s=pathlib.Path(sys.argv[1]);d=pathlib.Path(sys.argv[2]);t=s.read_bytes().decode('utf-8');t=t.replace('\r\n','\n').replace('\r','\n').replace('\n','\r\n');d.write_bytes(t.encode('gbk'));print(d,t.count('\r\n'),'lines')" .tmp_018_d_probe/utf8/install.bat scripts/install.bat
  ```
  **不要用 `sed -i` 改这些文件**：Git Bash 的 sed 会把 CRLF 全部吃掉（本次实测踩中，
  文件随即被 cmd 解析错乱）。

6.4 Batch 机制探针：LF 行尾的 .bat 会被解析错乱（probe.bat 实测）→ **必须 CRLF**；
    `py -3 -c "...version_info >= (3,10)..."` 的退出码分流正例（PY=py -3）与反例
    （门槛写 3.99 → PY 为空）都按预期；`py -9` 不产生噪音；`pushd %~dp0..` 后 `%CD%`
    得 E:\boardwise；`start "" /b cmd /c "for /l %%i ..."` 的并发输出与子进程继承当前
    目录都实测成立（这是轮询那一行的依据）。
6.5 **编码对照实验（决定 GBK 的那次）**：同一份 install.bat 头部，只改编码/首行命令跑
    对照——UTF-8（无 BOM）+ `chcp 65001`：输出里出现把注释行/echo 行**尾巴当命令执行**
    的报错（如 `'改系统' 不是内部或外部命令`），关键中文行直接丢失；UTF-8 + BOM：
    第 1 行 `@echo off` 失效、整脚本变回声；**GBK + `chcp 936`：零碎片、所有中文行完整、
    exit 0**。据此定稿为 GBK + chcp 936（并顺手修掉了 install.bat 里遗留的 `chcp 65001`）。
6.6 **变异验证（≥2 个靶点）**：
    - M1 install.bat 的 Python 门槛 `(3,10)` → `(3,99)`：脚本走"没有找到 Python"分支并
      exit 1，`.venv` 未被创建/改动（正例见 T1）；
    - M2 build-connector.bat 的 `LSS 20` → `LSS 99`：走"Node.js 版本太低"分支，exit 1；
    - M3 直接改 **shipped 文件** scripts/stop-daemon.bat 里的 `findstr /c:"LISTENING"` →
      `LISTENINGX`：假监听器活着时脚本走"没有在监听的进程"（说明这层过滤是承重的）；
      随后 `cp` 还原 + `sha256sum -c` 通过，哈希逐字节一致
      （7513b38a1c52b9588859fc30cc67f383d1b73cbe9993f7c3f8f2677663040937）。
    说明：§D 不改 Python/TS 代码，没有 pytest 可见的变异靶点；三个靶点都在脚本层，
    且 M1/M2 是在**副本**上做（shipped 文件从未被改），M3 走了完整的
    "改→红→还原→哈希一致" 流程，全程未用 git checkout。

七、存疑 / 偏差记录
--------------------------------------------------------------------------------

1. package.mjs 头部注释说 .eext 布局"not yet confirmed on a real sideload"，但 012/013 的
   真机记录显示多个版本侧载成功（编辑器里跑的就是 0.4.10）。这是**过时注释**，本次不动
   （改它超出 §D 权限，且要动 connector 源码——归后续维护者）。
2. package-lock.json 的 root name/version 与 package.json 不一致（connector@1.0.0 vs
   boardwise-connector@0.4.10）。实测不影响 npm ci，但属于潜在坑，已记在 1.8；
   刷新锁文件需要跑 npm install（本次禁止），故留给维护者。
3. 任务书 §D 第 3 条写"可见窗口起 daemon …，窗口内打印连接状态"，而 daemon 自己
   **只在启动横幅（cli.py）、首次配对公告（cli.py 的 on_pairing 回调）以及 §A 新加的
   "另一个编辑器实例已连接"拒绝提示（daemon.py 里唯一那处 print）时打印**，不会逐次报
   连接事件、也不会在扩展连上来时打印。我按"窗口内真的能看到连接状态"实现：在 daemon
   窗口里并发跑 60 秒一次的状态轮询（只打 connector: 那两行）。
   该并发构造已在 §6.3 的 T5 与 t4 探针里实测可行，但**整脚本未端到端执行**——那需要
   真起 daemon，按总纪律禁止。
4. 同理，install.bat **没有真正跑过安装**（会建 venv/装包，任务书明确禁止）：T1 是"只把 3 条
   会改机器的命令行换成 echo"的全文走查（结构、分支、路径、提示全部真跑），安装动作本身
   靠静态核查 + 上线后岳的朋友机实测。
5. 中文批处理的编码口径最终定为 **ANSI/GBK + CRLF + 第 2 行 `chcp 936`**（依据见 §6.5 对照
   实验）。代价要如实记一笔：**GBK 文件在 UTF-8 里看是乱码**，仓库里读/审这些 .bat 需要
   转一下（`iconv -f gbk -t utf-8 scripts/install.bat`）；这是"能在朋友机上正确显示并正确
   解析"换来的代价，若嫌别扭，替代方案是把脚本写成纯 ASCII + 中文另置文件，但那样每条提示
   都要多一个文件。当前的 UTF-8 母本留档在 `.tmp_018_d_probe/utf8/`（一次性证据目录，未入库）。
6. **顺带发现的既有缺陷（不在 §D 范围，未改）**：连接到一个"不是 daemon 的进程"时，
   `.venv\Scripts\python.exe -m boardwise.cli bridge status` 会抛未捕获的
   `websockets.exceptions.InvalidMessage`（cli.py `_cmd_bridge_status` 只 catch
   `(OSError, BridgeError)`），打印一大段 traceback。触发场景：61190 上被别人占了、
   或 daemon 崩在半路。影响：start-daemon.bat 的预检分支在那种情况下会显示 traceback
   （脚本本身仍正常退出 0）。修法很小（那个 except 加上 WebSocketException），
   但 cli.py 归其他执行者，故只报不改。
