# R4 阶段二安全设计草案（**只是设计，待评审，没有写代码**）

> 任务书原话：「安全面必须先写……这段设计先在 PR 里过审再写代码」。本文件就是那段设计。
> 前提：阶段一 ①② 通过（真机上 `new Function` 能用、`crypto.subtle` 存在）。前提不成立，本草案作废。

## 1. 威胁模型

- daemon 的 WS（`127.0.0.1:61190`）**没有认证**：本机任何进程都能连上，冒充 daemon 或往 daemon 推东西。
- 现在的配对是 TOFU 令牌，它防的是「陌生 connector 冒充」，**不防**「陌生载荷被 connector 执行」。
- stub 一旦能执行远端字符串，本机任何能连到这个端口的进程，就能在编辑器的扩展环境里跑任意代码。扩展环境能调 `eda.*`，也就能改、删、导出用户的工程。
- 所以要解决的问题是：**stub 只执行发布者签过名的载荷**，而且「谁能签」不能被本机其他进程控制。

## 2. 设计

1. **stub（极小、永远不变）**：随 `.eext` 发布，里面硬编码**一把发布者公钥**（Ed25519 或 ECDSA P-256，取决于宿主 WebCrypto 支持哪个；①的探针会给出答案）。私钥**不在**用户机器上，只在发布流程里。
2. **载荷**：`{version, sha256, code}` 加一个签名，签名覆盖 `version‖sha256‖code`。签名在发布时生成，作为 release 附件和 `.eext` 一起发。
3. **daemon 只负责转交**：daemon 把磁盘上的载荷和签名原样交给 stub。**daemon 不持有私钥**，所以 daemon 被替换也伪造不出合法载荷。这一点与任务书写的「daemon 侧持有公钥 / hash 白名单」**不同**，见 §4 的取舍说明。
4. **stub 的执行条件**：
   - 先用 `crypto.subtle.verify` 验签（用 stub 内置公钥），再核对 `sha256(code)`；
   - **版本单调（回滚保护）**：载荷除 `version` 外再带一个发布时分配的**单调递增序号 `seq`**（发布流程保证只增、不复用，且被签名覆盖）；stub 内置一个**最低序号地板 `minSeq`**，只执行 `seq ≥ minSeq` 的载荷。地板**只随 `.eext` 提升**（带外，与 stub 同一条通道），所以「签名合法但序号旧」的载荷在下一颗 `.eext` 之后一律被拒。
     **拒绝把「上次接受的版本/序号」记在扩展用户配置或 `~/.boardwise/` 里当信任根**——那同样是本机攻击面内的可写存储，抹回 0 再喂一个签名合法的旧载荷，单调性就失效。本地那份记录最多当**提示**：读到更低时在报告里标注，**不作为拒绝依据**。残余风险如实申报：两次 `.eext` 之间，发布者已签但事后撤回的载荷仍可能被重放，窗口由「发布者下一次提升地板的及时性」封顶。
   - 任何一项不过，就**不执行**，并回退到 stub 自带的「最小 connector」：只能回答 `ping` 和 `sys.connector_status`，并报告 `payload rejected: <原因>`。
5. **回退路径**：`.eext` 永远是完整 bundle 的一份，随发布件一起提供（任务书的要求），stub 失效时用户手动重装就能恢复。
6. **没有密钥管理就不上线**：私钥放在哪里（GitHub Actions secret 还是离线密钥）、怎么轮换、公钥换了以后旧 stub 怎么办（多公钥列表，加一个过期时间），这几件事主代理裁决前**不实施**。
7. **信任根：stub 只带外分发，永不接受在线更新自己**（评审 P1）：
   - 初次安装与每一次替换/升级都走**带外**通道（用户手动侧载 `.eext` / 应用商店 / 与 `boardwise install-skill` 同级的本地安装路径），**不经** `sys.self_update`。
   - 理由：今天把代码送进编辑器的通道 `sys.self_update` 走**无认证的 WS**（`daemon.py:897-899` 的 CLI 角色只要 daemon token，而该 token 就是本机磁盘上的一个文件；`:1564` 只按 role 放行）。若 stub 也走这条通道推送，攻击者先塞一个**持他自己公钥**的 stub，验签根即被替换，整套设计归零。
   - 因此 stub 生效后，`sys.self_update` 对 **stub 自身**被禁用（或至少收敛为「只接受已验签的载荷」，绝不接受裸 `bundleB64`）。
   - 一句话：**能换掉一颗已生效 stub 的公钥的，只有带外安装**——网络上的任何东西都换不掉它。

## 3. 读不到 `crypto.subtle` 时

- 不能退化成「只核对 hash 白名单」：白名单存在哪里都可能被本机进程改，比如 daemon 的磁盘或扩展存储。
- 这种情况的诚实结论是：**放弃 stub 方案，保留现在的「写入 + reload」通道**（本机实测可用）。任务书也写了放弃是合法结论。

## 4. 与任务书写法的偏差（请裁决）

任务书写的是「载荷要签名校验（daemon 侧持有公钥 / hash 白名单），stub 只执行验签通过的载荷」。
我的建议是**验签放在 stub 里、公钥也内置在 stub 里**，理由是：daemon 进程和它的磁盘都在本机攻击面之内，验签放在 daemon 侧，就等于信任 daemon；
放在 stub 里，攻击者必须拿到发布私钥才行。代价是：stub 的公钥要更换，就得重装一次 `.eext`。

## 5. 验收（与任务书一致）

- 换一次载荷（版本号变），不重载编辑器，`bridge status` 回读到新版本；
- 篡改载荷 1 个字节、换签名、换公钥、回滚版本这四种情况，stub 都拒绝执行，并报出原因（要有对应测试）；
- connector npm 全绿，并附安全评审记录。
