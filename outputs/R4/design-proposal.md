# R4 阶段二安全设计草案（**只是设计，待评审，没有写代码**）

> 任务书原话：「安全面必须先写……这段设计先在 PR 里过审再写代码」。本文件就是那段设计。
> 前提：阶段一 ①② 通过——真机上动态执行三通（`new Function` 回 42）。**`crypto.subtle` 在 realm 里是 `undefined`**
> （2026-10-13 真机读数 + 2026-10-17 `sys.probe {realm:true}` 复测），所以验签走 §3b 的纯 JS 路，
> 而不是初版假设的 WebCrypto。动态执行不成立，本草案才作废。

## 1. 威胁模型

- daemon 的 WS（`127.0.0.1:61190`）**没有认证**：本机任何进程都能连上，冒充 daemon 或往 daemon 推东西。
- 现在的配对是 TOFU 令牌，它防的是「陌生 connector 冒充」，**不防**「陌生载荷被 connector 执行」。
- stub 一旦能执行远端字符串，本机任何能连到这个端口的进程，就能在编辑器的扩展环境里跑任意代码。扩展环境能调 `eda.*`，也就能改、删、导出用户的工程。
- 所以要解决的问题是：**stub 只执行发布者签过名的载荷**，而且「谁能签」不能被本机其他进程控制。

## 2. 设计

1. **stub（极小、永远不变）**：随 `.eext` 发布，里面硬编码**一把发布者公钥**（Ed25519；探针已给出答案：realm 里 `crypto.subtle` 是 `undefined`，所以验签必须走纯 JS 实现——§3b，不能用 WebCrypto 的 Ed25519 或 ECDSA P-256）。私钥**不在**用户机器上，只在发布流程里。
2. **载荷**：`{version, sha256, code}` 加一个签名，签名覆盖 `version‖sha256‖code`。签名在发布时生成，作为 release 附件和 `.eext` 一起发。
3. **daemon 只负责转交**：daemon 把磁盘上的载荷和签名原样交给 stub。**daemon 不持有私钥**，所以 daemon 被替换也伪造不出合法载荷。这一点与任务书写的「daemon 侧持有公钥 / hash 白名单」**不同**，见 §4 的取舍说明。
4. **stub 的执行条件**：
   - 先**验签**（用 stub 内置公钥 + §3b 的纯 JS 验签器；realm 里没有 `crypto.subtle`，不许写成 `crypto.subtle.verify`），再核对 `sha256(code)`；
   - **版本单调（回滚保护）**：载荷除 `version` 外再带一个发布时分配的**单调递增序号 `seq`**（发布流程保证只增、不复用，且被签名覆盖）；stub 内置一个**最低序号地板 `minSeq`**，只执行 `seq ≥ minSeq` 的载荷。地板**只随 `.eext` 提升**（带外，与 stub 同一条通道），所以「签名合法但序号旧」的载荷在下一颗 `.eext` 之后一律被拒。
     **拒绝把「上次接受的版本/序号」记在扩展用户配置或 `~/.boardwise/` 里当信任根**——那同样是本机攻击面内的可写存储，抹回 0 再喂一个签名合法的旧载荷，单调性就失效。本地那份记录最多当**提示**：读到更低时在报告里标注，**不作为拒绝依据**。残余风险如实申报：两次 `.eext` 之间，发布者已签但事后撤回的载荷仍可能被重放，窗口由「发布者下一次提升地板的及时性」封顶。
   - 任何一项不过，就**不执行**，并回退到 stub 自带的「最小 connector」：只能回答 `ping` 和 `sys.connector_status`，并报告 `payload rejected: <原因>`。
5. **回退路径**：`.eext` 永远是完整 bundle 的一份，随发布件一起提供（任务书的要求），stub 失效时用户手动重装就能恢复。
6. **没有密钥管理就不上线**：私钥放在哪里（GitHub Actions secret 还是离线密钥）、怎么轮换、公钥换了以后旧 stub 怎么办（多公钥列表，加一个过期时间），这几件事主代理裁决前**不实施**。
7. **信任根：stub 只带外分发，永不接受在线更新自己**（评审 P1）：
   - 初次安装与每一次替换/升级都走**带外**通道（用户手动侧载 `.eext` / 应用商店 / 与 `boardwise install-skill` 同级的本地安装路径），**不经** `sys.self_update`。
   - 理由：今天把代码送进编辑器的通道 `sys.self_update` 走**无认证的 WS**（`daemon.py:897-899` 的 CLI 角色只要 daemon token，而该 token 就是本机磁盘上的一个文件；`:1564` 只按 role 放行）。若 stub 也走这条通道推送，攻击者先塞一个**持他自己公钥**的 stub，验签根即被替换，整套设计归零。
   - 因此 stub 生效后，`sys.self_update` 对 **stub 自身**被禁用（或至少收敛为「只接受已验签的载荷」，绝不接受裸 `bundleB64`）。
   - 一句话：**能换掉一颗已生效 stub 的公钥的，只有带外安装**——网络上的任何东西都换不掉它。

## 3. 读不到 `crypto.subtle` 时

- 不能退化成「只核对 hash 白名单」：白名单存在哪里都可能被本机进程改，比如 daemon 的磁盘或扩展存储。
- 2026-10-13 真机读数确定了这一条：realm 里 `crypto` 在、**`crypto.subtle` 是 `undefined`**（`outputs/R4/live/realm_probe_0.5.12.json`），所以草案初版在这里写的「放弃 stub 方案，保留写入 + reload 通道」**不再是唯一出路**——验签可以用纯 JS 实现，见 §3b。
- 放弃仍然合法：§3b 的结论要岳裁；若 §3b 的推荐不被接受，本条就是退路（现在这条通道本机可用）。

## 3b. 纯 JS 验签（2026-10-17 调研 + 本机自检，R4a）

**结论先说**：`crypto.subtle` 缺席**不构成**放弃签名校验的理由。Ed25519 的验签是纯整数运算 + 一个 SHA-512，两样都能用普通 JS 写，**不需要任何宿主 API**。

### 候选库（只调研，未安装；`npm view` 只读）

| 包 | 版本 | unpacked | 依赖 | 许可 | 需要 `subtle`？ |
|---|---|---|---|---|---|
| `tweetnacl` | **1.0.3** | 174 912 B（11 文件） | **0** | Unlicense（公共领域） | **不需要**。自带 `nacl.hash` 的 SHA-512 与全部曲线运算；`nacl.sign.detached.verify(message, signature, publicKey)` 是**同步**布尔返回。Verifying 路径不碰随机数（只有 keygen/sign 需要 `crypto.getRandomValues`，本设计不用） |
| `@noble/ed25519` | 3.2.0 | 120 259 B（6 文件） | 0（自带） | MIT | **需要**。README：默认只给 async 方法；同步方法要自己把 SHA-512 挂上去（`ed.hashes.sha512 = sha512`，来自 `@noble/hashes`），而默认的 async 路径走的就是 WebCrypto —— 本 realm 里 `subtle` 是 `undefined`，async 路直接不通 |
| `@noble/hashes`（上一条的配套） | 2.4.0 | 691 646 B（60 文件） | 0 | MIT | 不需要（纯 JS `sha2.js`），但只为 sha512 引入这一整包 |

**推荐：`tweetnacl@1.0.3`，版本钉死。** 理由：①零依赖、纯 JS、`Unlicense`（公共领域，内嵌进 stub 没有许可负担）；②**Cure53 2017 年审计过**（tweetnacl README 附完整报告），比自写实现少一份「谁审这段密码学代码」的账；③verifying 路径不需要随机数，不需要 `crypto.subtle`，也不需要给任何 `hashes` 钩子赋值——一个 `require`/import 就能用，正是「stub 极小且永不变化」想要的形状；④同步 API 让 stub 的执行路径不必引入 async/await 与微任务时序（菜单点击求值、快速重连这些场景里，少一层就行）。

`@noble/ed25519` 落选的原因不是质量问题（它的实现更现代、常量时间意识更强），而是**在我们这个 realm 里它要额外挂一个 SHA-512 来源**：挂 `@noble/hashes`（+0.7 MB unpacked）或自己喂一个 sha512，等于多一条必须在真机复验的接线；而它默认的 async 路依赖的正是那个缺席的 `crypto.subtle`。

### 本机自检（证据 `outputs/R4/live/r4a_04_ed25519_selfcheck.txt`，仪器 `live/r4a_ed25519_selfcheck.mjs.txt`）

一份**内联的**最小 Ed25519 verify（自写，纯 JS，`new Function` 执行，源码 5 573 字符 / esbuild 压后 **2 786 字符**，压后那份也实测跑通——见下）在下面条件下逐条通过：

- `Object.defineProperty(globalThis,'crypto',{value:undefined})` —— 模拟 realm 的「没有 WebCrypto」；
- 经 `new Function(source)()` 执行——**与 stub 执行载荷同一条路径**（该路径本身已在 2026-10-13 真机上验过：`newFunction.ok = true` 回 42）；
- RFC 8032 §7.1 的 TEST 1/2/3（空消息、1 字节、2 字节）三个官方向量全部 `true`；
- **独立对拍**：同样的三个向量交给 `node:crypto`（另一份实现）也全部 `true`，所以「向量记错」不会伪造成「实现正确」；
- 负对照 **5 条全部 `false` 且不抛异常**：签名在 `R` 里翻 1 bit（byte 3 / byte 10 各一）、在 `S` 里翻 1 bit（byte 40）、消息翻 1 bit、以及一整条垃圾 64 字节签名；
- 自检里没有任何表常量可以记错——SHA-512 的 80 个 K 与 8 个 H 都是运行时从素数立方/平方根推出来的，摘要先与公开的 `SHA-512("")` / `SHA-512("abc")` 对上才开始验签。

**自写实现踩到的第一个坑（留给 R4b 的教训，也是推荐用审计过库的一条实证）**：第一版 verifier 在「签名的 `R` 解压失败」时**抛 TypeError 而不是返回 false**（`add()` 拿到 null 就解引用）——官方向量全过、负对照里恰好挑中的那一个字节也没暴露它，是第二次换了一个字节位置才炸出来的。修法是**在构造右式之前先判空**（拒绝，不是异常）。安全面上的口径应当是：**验签器对任意畸形输入只能答 `false`，绝不许抛**；这一条要写进 R4b 的拒绝用例（§5）。

**压后的形态有一条执行契约的坑**：`esbuild --minify` 出来的 2 786 字符那份，用 `new Function(code)`（函数体形态）或 `eval(code)` 执行都正常（三个向量仍 `true`、负对照 `false`），但**包成 `return (code)` 表达式形态会报语法错**（本机实测：`SyntaxError: Unexpected token ';'`）。载荷的执行契约要在 R4b 里**明确选一种**（函数体 + 显式 `return`，或 `eval` 表达式形态），并让构建器输出与之匹配的形态，别假设「随便包一下就能拿到返回值」。

**没做到的、如实写**：这段自检**不在编辑器 realm 里**跑，只在 Node + 无 `crypto` 全局的条件下跑。原因：现有探针通道**按设计不接受任何代码**（`sys.probe {realm:true}` 是布尔开关，`params` 里的东西一律不执行，见 `connector/src/actions.ts` 的 `realmProbe`）。要把它变成 realm 内的读数，需要 R4b 加一个**只读的常量自检动作**（形状抄 `realmProbe`：向量与代码都写在 connector 里、不接收入参、回 `{vector, ok}`），而不是给探针开一个「传字符串进来执行」的口子——那正是本设计想避免的面。在 R4b 那一小段落地前，「realm 内能验签」是**推断**（本机自检 + 真机已证的 `new Function` 通路），不是实测。

### 密钥管理：三选项（**不替岳选**，只列利弊 + 推荐理由）

**① GitHub Actions secret 签名（发布流水线里签）**
- 利：签名与构建同一条流水线，人为漏签不可能（同一 job 里 build → sign → upload）；私钥不出 CI 的 secret 存储；版本/序号可在签名脚本里强制单调。
- 弊：信任根搬到 GitHub（仓库被入侵、Actions secret 被读走 = 私钥泄漏）；本机离线发版（`packaging/build_exe.py` + `gh release create` 是现在真在用的路径）反而绕开流水线，会出现「两种发版路径、只有一种会签」的分叉；轮换私钥要走一次 CI 改密。
- 要求：签名必须覆盖 `version‖seq‖sha256(code)` 并**把 sha256 写进 release notes**（今天已经在算 bundle 哈希，接口现成）。

**② 本机离线私钥、发版时手签**
- 利：私钥只在一台机器的一个文件里（可放 U 盘/离线），GitHub 与 CI 都不持有；与现状发版流程（本机 `npm run package` + `build_exe.py` + `gh release`）零冲突；轮换是换文件。
- 弊：**人手一步**，忘了签或签错版本没有机器拦；私钥文件在那台机器上被读走 = 全盘失守（没有 HSM，也没有第二把锁）；岳不在时就发不了版（应急路径要另外写）。
- 要求：签名脚本 + 校验脚本成对入库，发版清单里加一条「签名附件已上传且 `verify` 回 true」。

**③ 两把公钥（主 + 备）内置 stub，带过期时间**
- 利：主私钥丢失/泄漏时有**备用路径**而不必立刻换 `.eext`（换公钥要用户手动重装，见 §2.7）；过期时间给旧公钥一个自动退场机制，也让「备用」不至于永久有效。
- 弊：**同时**多一个可被滥用的信任根（任一私钥泄漏都等价于全泄）；过期时间引入新的失败模式（忘了续期 = 合法载荷被拒、用户看到 stub 罢工）；stub 里多一段时钟判断——而**时钟不作数**（本机时钟可改，只能当提示，不能当拒绝依据，和 §2.4 里「本地记录只当提示」同一条纪律）。
- 要求：过期只能**降权**（过期公钥不再接受新发布，但仍可验证已发布版本？——这一条要给岳一个明确口径，否则就是含糊的信任根）。

**推荐理由（供裁决，不是决定）**：先做 **②**，把机器化的部分（签名脚本、`verify` 校验、sha256 进 release notes）做成一条命令，人手只负责「跑命令 + 上传附件」；等发版频率真正变高、或岳需要别人代发版时，再升到 **①**（那时把同一条命令搬进 CI 即可，签名格式不变）。**③ 不要在阶段二第一版就上**：它是为「私钥出事」准备的冗余，而不是为「日常发布」准备的，先上会让信任根的数量翻倍，而 §2.4 的单调性论证要跟着复杂一档。

## 4. 与任务书写法的偏差（请裁决）

任务书写的是「载荷要签名校验（daemon 侧持有公钥 / hash 白名单），stub 只执行验签通过的载荷」。
我的建议是**验签放在 stub 里、公钥也内置在 stub 里**，理由是：daemon 进程和它的磁盘都在本机攻击面之内，验签放在 daemon 侧，就等于信任 daemon；
放在 stub 里，攻击者必须拿到发布私钥才行。代价是：stub 的公钥要更换，就得重装一次 `.eext`。

**由此推出一条对实现方的硬要求：daemon 侧不需要任何密钥材料**——它不持有公钥、不持有 hash 白名单、不参与验签，
只把磁盘上的 `{version, seq, sha256, code}` 与签名原样转交给 stub（§2.3）。这条要在协议与代码评审里都对得上：
daemon 一旦出现「公钥/白名单」形状的常量或配置，「验签在 stub」这个决定就被架空成两层信任，攻击面翻倍。
（`crypto.subtle` 缺席不影响这一条——纯 JS 验签同样只在 stub 侧跑，见 §3b。）

## 5. 验收（与任务书一致）

- 换一次载荷（版本号变），不重载编辑器，`bridge status` 回读到新版本；
- 篡改载荷 1 个字节、换签名、换公钥、回滚版本这四种情况，stub 都拒绝执行，并报出原因（要有对应测试）；
- 纯 JS 验签（§3b）的**验签器自身**要有官方向量测试（RFC 8032 §7.1）与负对照，且实现选型落定后版本钉死；
- realm 内验签要有**真机读数**（R4b 的常量自检动作），不能只停在 Node 侧的推断；
- daemon 侧**零密钥材料**（§4）要有代码/评审层面的钉子（如「daemon 源码里不得出现公钥常量」的测试）；
- connector npm 全绿，并附安全评审记录。
