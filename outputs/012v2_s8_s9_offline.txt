三、§八 `review.mark` 实现要点（任务书 69–75 行）
================================================================================
连接器动作签名：
  review.mark
    params { pageUuid?, marks:[{ref,ruleId,severity,text}], clear?, focus?, color?, zoom?, markers? }
    返回   { mode:'markers'|'list', cleared, page:{components,designators,withoutPosition,active},
             count, marked:[{position,marker,ref,designator,ruleId,severity,text,primitiveId,x,y}],
             unresolved:[{position,ref,ruleId,severity,text,reason}],
             markers:{attempted,accepted,reason?}, focused?:{position,ref,x?,y?,zoomed,reason?},
             readOnly:true, note, notes? }
    risk = read（标记是叠加层，不建不改任何图元；与 canvas.highlight 同级）
    daemon 超时 = 默认 30s（与 sch.geometry 同为一次页面 dump + 一次打标调用；未新增常量）

1) 位置来源 = `sch.geometry` 的同一套 dump（geometryOf('sch_PrimitiveComponent') → state.Designator /
   state.X / state.Y；Designator 缺失时兜底 state.OtherProperty.Designator）。**整页只读一次**，
   而不是每个 ref 一次 locate()——打标本来就需要全部坐标。
   页面读不出来（命名空间缺失/抛异常）是**结构性失败**（CONNECTOR_ERROR 并点名原因），
   不降级成"空跳转清单"：一份空清单说不出为什么空。
   没有位号或没有数值坐标的图元计入 page.withoutPosition 并在 notes 里说明，不静默丢弃。
2) 打标内容（任务书要求 rule-id + severity + 一句话）：`generateIndicatorMarkers` 的声明形态是
   `(markers: IDMT_IndicatorMarkerShape[], color?, lineWidth?, zoom?)` —— **只能画形状，不能写文字**
   （形状仅 point/circle/line/arc/rectangle）。故：每个 ref 画一个以其坐标为中心的矩形，
   文字三件套随结果返回，`marked[k-1]` 就是画布上第 k 个 marker。
   CLI 打印的"序号 ↔ marker#k"表就是这张图的图例 —— 没有它，画布上那堆框没有意义。
   矩形字段名沿用 canvas.highlight 的实测教训：left/right/top/bottom（不是 startX/endX）。
   **不做按 severity 分色**：颜色属于"这次调用"而非单个 marker，分色 = 每种严重级别一次调用，
   属未裁决的设计决策，本批不擅自决定（已在 docs/bridge.md 写明）。
3) 降级纪律（任务书 §八 末条）—— 降级分支**三条都有测试**，且都不丢发现清单：
   a) `markers:false`（调用方明确只要跳转清单）；
   b) 宿主没有 `generateIndicatorMarkers`（typeof !== function）；
   c) 宿主返回 false（不支持该画布 / tabId 未知）。
   三者都 → `mode:'list'` + markers.reason，坐标照常返回。CLI 对应退出码 1（部分完成）。
   单个 ref 不在本页 → 逐条 `unresolved`（reason 写清"本页 N 个位号 / M 个图元"），其余照画。
4) 结构性拒绝（一律 throw，不静默）：
   - `pageUuid` 与焦点页不符 → PAGE_MISMATCH（**守卫在读坐标之前**，错误页不会画出任何东西）；
   - 焦点文档不是原理图页（dmt_SelectControl 读数：pcb/其他）→ CONNECTOR_ERROR，写明"会画到错的画布上"；
   - 页面组件读不出来 → CONNECTOR_ERROR；
   - `focus` 超出 marks 范围或非整数 → BAD_REQUEST（同样在画任何东西之前）；
   - marks 为空且非 clear → BAD_REQUEST；
   - `clear:true` 而宿主没有 `removeIndicatorMarkers` → NOT_IMPLEMENTED
     （"移除叠加层"没有跳转清单式退路）。
   `focus: N` 为 **marks 的 1-based 位置**（= 调用方自己的发现顺序，即 `boardwise review` 的报告顺序）；
   zoomToRegion 收到的四个参数按声明顺序 `(left, right, top, bottom)`，盒子 = marker 框 + 20 单位余量；
   focus 与 zoom 同时给时 **focus 赢**（否则"看到哪个框"取决于调用顺序）。
   zoomToRegion 缺失 / 返回 false / 抛异常 → focused.zoomed=false + reason，**不影响已打好的标记**。
5) CLI（`src/boardwise/cli.py`）：
   `boardwise review-mark <findings> [--page UUID] [--focus N] [--color C] [--zoom] [--no-markers] [--json PATH] [--port N]`
   - `<findings>` 三种形态：文件路径 / `-`（stdin）/ JSON 字面量（既不是文件也不是 `-`，
     且以 `{`/`[` 开头才当字面量，路径优先）。接受 `review --json` 的 `{summary,findings}`、
     裸数组、单条 finding 三种载荷；形状不对 → 退出 2 并说明期望什么。
   - 字面量 `clear` = 清标（与任务书 `review.mark clear` 对应）；与既有 `bridge highlight --clear` 同一语义。
   - 一条发现 → **每个 ref 一个 mark**（去耦类发现同时点名 IC 和电容，两个都要亮），
     mark 顺序 = finding 顺序 = ref 出现顺序（`--focus N` 数的就是这个位置）。
     没有 ref 的发现进 `skipped` 并在表里以 `[~]` 行点名（不静默少一条）。
   - 退出码：0 全部到位 / 1 部分到位（含降级为 list、有 skipped、有 unresolved、clear 被拒）/ 2 输入或 daemon 不可用。
   - 打印：`[k] 级别 规则 位号 marker#N @ (x, y) 一句话`；降级/notes/focused 逐行说明；末尾提示 clear 命令。
6) 报告侧配套（`engines/review.py`）：`render_json` 每条 finding 增 `refs`（由 evidence→message
   顺序派生、去重），规则本身**未改一行**（不是让 15 条规则各自声明 refs）。
   抽取用**前缀白名单**（复用 `core/parts.DESIGNATOR_CATEGORIES` 的前缀 + RV/RP/RT/FB/NT/ZD/TVS/VR/BT/MK/MIC/TH/ZZ）：
   只按形状匹配会把 `AMS1117` / `SS34` / `CH340G` / `FRC0805J471` / `PC14` / `D5V` 全当位号
   （前两个实测会命中），这些正是会变成"解析不到"噪音的东西——白名单有专门的参数化测试。
