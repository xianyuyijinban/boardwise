## 2026-03-15 - LCD Blank Screen Debugging Lessons

- 遇到了什么问题
  - LCD 一直是背光亮但无显示。
  - 我在没有先核实当前 PCB 实际引脚映射的情况下，直接套用了参考工程的 LCD 控制脚映射，把排查方向带偏了。
  - 我增加了启动纯色自检，但把背光打开动作放在自检之后，导致自检实际不可见，进一步误导了判断。

- 如何解决的
  - 以用户提供的屏幕引脚图为准，确认当前板级映射是 `PA5=SCK`、`PA7=MOSI`、`PC4=RES`、`PC5=DC`、`PB0=BLK`，不再继续沿用参考工程的 `PB0/PB1/PA4` 控制脚定义。
  - 在 `st7789` 初始化路径中把背光打开时序提前到启动纯色自检之前，保证 `红/绿/蓝/白` 自检对人眼可见。
  - 用运行计数器验证 MCU 端确实持续执行了写屏命令和整屏填充，避免把 UI 层问题和面板初始化问题混在一起。

- 以后如何避免
  - 任何板级调试，先以当前 PCB/网表/用户实拍为唯一真值，再参考示例工程；未经核实，不允许替换控制脚定义。
  - 新增“可见性自检”时，先检查背光时序，再根据肉眼现象做判断；没有背光就不能把“黑屏”当成写屏失败证据。
  - 显示问题按三层拆开排查：`背光是否打开`、`总线是否在写`、`面板是否显示`。每次只改一层，不跨层猜。

## 2026-03-16 - ESP8266 WiFi and MQTT Debugging Lessons

- 遇到了什么问题
  - ESP8266 接回 STM32 后，AT 指令链路不稳定，`AT` / `CWJAP` / MQTT 建链回复会丢失，表现为 WiFi 偶发连接、MQTT 长时间停在初始化或反复断开。
  - LCD 上的 WiFi 状态是根据粗粒度 `esp_state` 推断的，导致真实已连上热点时仍显示 `disable` / `disconnected`，热点断开后又可能继续显示 `connected`。
  - 当前 EMQX Cloud 部署并没有开放明文 MQTT `1883` / `8083`，但代码仍尝试走明文端口，导致原始 MQTT 连接建立后马上失败。
  - RAW MQTT 发送 `CONNECT` 报文后，代码把 `SEND OK` 当成 broker 已连接成功，没有等待 `CONNACK`，把“套接字发送成功”和“MQTT 协议握手成功”混为一谈。

- 如何解决的
  - 调整 ESP8266 AT 命令接收策略，在命令会话期间保持 UART IRQ 接收持续开启，不再让命令路径和异步接收路径互相抢状态。
  - 增加 AT 探测策略，补上波特率探测与 boot-ready 延时，降低模块上电初期还没稳定就发送 AT 的失败概率。
  - 修正 WiFi 连接启动条件，让 `RESET` / `INIT` 状态也允许重进连接流程；LCD 显示改为直接使用 `app_wifi_connected`，不再从 `esp_state` 猜测。
  - 将 EMQX Cloud 路径固定为 `8883` 原始 SSL 套接字，并在 RAW MQTT 传输层显式等待 `CONNACK` 后才把状态推进到 `MQTT_CONNECTED`。
  - 通过主机侧测试、Keil 全量编译、板上符号观测和 PC 订阅验证四层交叉确认：设备可稳定上线、周期发布传感器数据，并能响应控制主题。

- 以后如何避免
  - 串口模组联调时，先确认“接收链路是否持续有效”，再查上层协议；如果底层 RX 中断策略不稳，后面所有 AT/MQTT 现象都会失真。
  - 云端接入前先做端口可达性核验，不允许默认假设 `1883` / `8083` 可用；部署文档、实测连通性和代码配置必须三者一致。
  - MQTT 状态机必须以协议确认包为准，不能用 `SEND OK`、socket open 之类的传输层信号替代 `CONNACK`。
  - 面向用户显示的连接状态必须绑定真实业务状态位，不能用内部中间态枚举做推断，否则调试会被 UI 假象带偏。

## 2026-03-16 - SmartMedicineBoxApp Dirty Submodule Cleanup Lessons

- 遇到了什么问题
  - 根仓库长期显示 `SmartMedicineBoxApp` 子仓库为脏状态，导致很难判断当前到底是源码未提交，还是只是本地缓存、APK、签名配置等生成物残留。
  - 子仓库里真实源码整理、文档删除、测试新增与本地 Gradle/Codex 目录、APK 产物混在一起，既影响判断，也影响后续合并分支时的可追踪性。

- 如何解决的
  - 先在 `SmartMedicineBoxApp` 内区分“应保留的源码改动”和“应忽略的本地生成物”，只为明显的本地目录与产物补充 `.gitignore` 规则，不误伤源码新文件。
  - 使用仓库自带的 `gradlew.bat` 对当前应用状态执行 `:app:compileDebugKotlin`、`:app:testDebugUnitTest`、`:app:lintDebug` 验证，确认这批整理后的源码可编译、可测试、可通过 lint。
  - 将子仓库有效改动单独提交，再回到根仓库提交 submodule 指针更新，恢复顶层仓库可审查、可合并的状态。

- 以后如何避免
  - Android 子仓库的源码改动和本地产物必须同步收口：新增本地工具目录时，第一时间补 `.gitignore`，不要等到根仓库被拖脏后再集中清理。
  - 子仓库有一批完整源码改动时，先在子仓库内完成构建验证并提交，再让根仓库跟随更新 gitlink；不要长期把“未提交源码”和“临时产物”堆在同一个脏工作区里。
  - 对带 submodule 的仓库，根仓库出现 `m <submodule>` 时，先进入子仓库做分类核查，再决定是提交、忽略还是删除，不能直接把所有脏项都当缓存处理。
