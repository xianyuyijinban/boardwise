# 任务书：V4 审查线差分调研（2026-10-31）

## 目标

在 0.6.0 后的正式适配前，基于仓库代码、已有 V4 真机记录和公开证据，回答：
V3→V4 的包/宿主变化会让审查线哪些输入、解析、在线采集、规则、报告和验证环节需要修改；
哪些不应改。只调研，不实施。

## 必须区分的输入

- V3/V4 本地 `.eprj2` SQLite 工程壳；
- 导出的 `.epro2` 工程归档及其内部 `.epru` / 原理图记录；
- `.eprj3` 文件夹工程；
- 在线 connector API 与归档读取不是同一证据通道。

不得用「V4 包不一样」推导整条 parser 都要改，也不得以旧实测推断当前版本已支持。

## 调研范围

1. `tasks/038-eprj3-tierA.md` 的 V4.1.60 实测、V4 正式适配清单及遗留样本缺口。
2. 当前 parser/CLI/checkup 实际入口与格式分派；原理图、PCB、网表、DRC/ERC、图像、
   review-evidence、export/fab 各通道对包格式和在线 API 的依赖。
3. connector/DSH 工具面、版本/页型守卫与 V4 在线兼容所需复测；区分已实测与未实测。
4. 规则引擎、报告 schema、DesignIntent、结论/triage/finalize 哪些是格式无关、应冻结。
5. 0.6.0 后「网表→类 C 的 AI 电路语义层」应挂在哪个共享语义边界，避免为 V3/V4
   各写一套业务解释器；本批只提接口约束，不设计实现。

## 交付

主代理汇总 `outputs/review/v4-review-line-research.md`，至少包含：

- V3/V4 输入形态与现有证据矩阵；
- 当前审查链逐项「可复用 / 需复测 / 需适配 / 缺样本」；
- 修改点精确到模块/入口，不写空泛“支持 V4”；
- P0/P1/P2 小批顺序、每批完成条件与所需真机/真实样本授权；
- 不做项、未证实项和 AI 语义编译层的后续接口约束。

## 边界

只读代码和公开夹具；不写生产代码、不改 fixtures、不做 git 写、不连接或操作编辑器、
不读取真实工程、不安装软件、不发 issue/Release。缺 V4 真样本就明确挂起，不用合成样本
冒充，不把旧 V4.1.60 结果当成当前 V4 全兼容证据。
