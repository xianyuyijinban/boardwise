# 测试为什么没拦住 —— 161 挖洞的流程复盘（2026-10-12）

> 起因：岳问「随便一扫就 30 多个洞，开发测试流程是不是有问题」。本文是根因归类与
> 流程对策。实例编号见 `tasks/161-hole-triage.md`。

## 先说公道话

5000+ 测试不是没用——每批的变异抽验全被抓，套件证明的是「**没变**」。问题是我们要的
是「**没错**」。这两者之间的缝，就是 30 个洞全部的来路。按根因归类，六类：

## 模式 1：钉住现状 ≠ 钉住真相

Golden-master 钉值把代码当天的输出封为真理；代码错，错答案就进钉，之后套件一直在
证明「错得很稳定」。

实例：H1（ARC 顶点错位被钉成「解析结果」）、G1/G2（错误的最近对被钉成净空值）、
D4（永远匹配不上的正则钉在名单里）。

防线：
- 翻钉必须附「新值为何是真相」的**独立推导**（已在执行，此处明文固化）；只有
  「新值是新代码算出来的」的翻钉在收口时拒收。
- 承重计算配一把**独立 oracle**：暴力枚举对拍（162a 的 8+6 随机板）、双实现互证、
  手工算一个数。

## 模式 2：测试形状 ≠ 生产形状

测试 helper 绕过生产接线（`run_pcb_review` 不传 `model=`、fake client 的 doc.open
永远成功），测的是平行宇宙——生产路径里的真分支在测试里从未被执行。

实例：F 系列（131b/d/e/f 钉了一年 PCB 占位假值，生产却走原理图）、P1（lint --page
的 fake 不会演「doc.open 没切过去」）、163b 拿历史快照当活体证据。

防线：
- helper 必须走生产入口（169/170 已修完全部实例）；
- **反模式进架构测试**（grep 级禁令）：`run_pcb_review(path)` 不传 model、
  `_load_model(view="pcb")` 当 ctx.model 传；
- fake 必须能演宿主的失败模式（167 给 fake 补「doc.open 会移动焦点」就是样板）。

## 模式 3：静默分支

`except: continue`、`or ""`、找不到就回退——每个静默分支都是一条没人看的缝。

实例：166 的 runner 吞规则（59→57 不可复现）、F3 多板静默取 board[0]、F5 负压轨
被丢、P4 零文本节点报 clean、D2 EARTH 从所有域消失。

防线：**静默分支登记制**——要么发 note、要么注释明写「为何沉默是对的」并进登记清单，
meta-test 钉住清单（变动必过审）。169 的 rulesErrored 是正面样板。

## 模式 4：两把尺 / 两条路

同一件事两条代码路径，必然漂移；测试往往只压其中一条。

实例：165（单窗路径补了 confirm、--all 没有）、E3（搜索时避让、终检没有）、
G4（文档说向下、代码向上，测试钉的是代码）。

防线：能抽同一把尺就抽（168 的 `annotation_foreign_wire_contacts`，solver/replay
共用）；抽不了就加「两路对拍」测试。

## 模式 5：没有不变量/属性测试

最伤的全是**不变量**破坏：粗筛必须下界真值、报告声称 ⊆ 实际跑了、在线 ≡ 离线。
断言具体数值的测试看不到这类错，因为错数值也会老老实实等于它自己。

防线：给承重不变量配属性测试（随机合成 + 暴力 oracle），162a 已立样板。清单：
解析往返（parser 输出顶点 ∈ 原始记录）、粗筛下界、coverage 声称 ⊆ 实跑、
在线 ≡ 离线对拍、两视图一致性。

## 模式 6：真机 / 真数据断层

写≠激活、冷导出缺层、daemon 死了——只在真宿主上可见。

防线：发版真机冒烟清单（下）。

## 流程对策（可执行清单，自此版起生效）

1. **挖洞常态化**：每波功能落地后派一轮只读审计 swarm（六缝模板见 tasks/161 的
   派发记录）。一次 ~10 分钟，本轮 ROI：30 洞。
2. **探针转回归 + 翻钉给据**：红先行；翻钉附独立推导（模式 1）。
3. **承重不变量属性测试层**：按模式 5 的清单逐波补。
4. **测试形状反模式进架构测试**（模式 2）。
5. **静默分支登记制**（模式 3）。
6. **发版真机冒烟清单**（模式 6）：`bridge status` / 在线 checkup vs `--file` 对拍 /
   `update-connector` 验收话术 / `draw lint` test 工程各一次，全部只读。
7. **每版人读一份报告**：挑一块真板把报告从头读到尾（166 就是这么被抓到的——
   「声称完整但一栏是空」只有眼睛能抓）。

## 发布闸（岳 2026-10-12 立，硬闸不议价）

版本按**议题闭环**发，不按批次发；同一日历日原则上只发一版（致命热修除外）。
发版之前三闸全过，缺一不发：

1. **挖洞测试**：对自上一版以来的 delta 派一轮审计 swarm（六缝模板，
   tasks/161 有派发记录）。发现的洞要么修、要么显式豁免并写进 release notes。
   挖洞是开发流程的**常驻环节**——每波功能落地后主动派，不等人喊。
2. **上机测试**：真机冒烟清单（test 工程，只读）：`bridge status` /
   在线 checkup 与 `--file` 对拍 / `draw lint` / 涉及桥动作变更时新动作真机走通。
3. **实测**：将发布的 exe 重打并冒烟（隔离端口自动拉起 + status）、三件套
   （exe/connector/dsh）构建齐、install-skill 双端同步、全量测试套件绿。

三闸全过 → `gh release`。任何一闸不过 → 修完重过，不带病上线。
背景：v0.5.9/v0.5.10 同日连发，现场机器当天就踩中 165/166 两个真 bug——
「发出去再被用户测出来」到此为止。

**版本号纪律（岳 2026-10-13 立）**：connector 版本与发布版本一致（v0.5.11 起
`connector/package.json` = `connector/extension.json` = 发布号），且
`src/boardwise/__init__.py` / `pyproject.toml` 同号（此前恒 0.1.0 是老 wart，
`--version` 报不出真版本）。历史散文里的版本语义随之改写——不存在过的中间号
（如 0.4.31）不许出现在对外文档。
